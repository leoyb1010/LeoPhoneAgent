# leocodebox 1.61.0 — 「更新失败 / 无法检查 / 独立副本」的真正根因

这个问题被反复修过多次都没根治,因为之前修的都不是根因。这次找到了。

## 根因一:安装/更新**完全没有** EBADF 重试(所以「更新失败」)

`runCliCommand` 里有这么一段:

```ts
if (timeoutMs > PROBE_TIMEOUT_CEILING_MS) {
  return runCliCommandUnthrottled(...);   // ← 提前 return
}
// ↓ EBADF 重试循环在这下面,永远轮不到上面那条路径
```

那条提前 return 的**本意**只是让长耗时的安装/更新**不占用并发闸**(否则它会把探针槽位占住几分钟)。但它把**重试也一起绕过了**——而重试循环恰好写在闸的下面。

结果:安装/更新用的是 300 秒超时(> 30 秒上限),于是走那条提前 return,**一次 EBADF 重试都没有**;而普通状态探针(5 秒超时)有 5 次重试。偏偏 npm 安装/更新自己要 spawn 大量子进程,正是 EBADF 竞态最容易发生的时刻——所以更新几乎必然撞上,并直接以 `which claude: spawn EBADF` 失败。

**修复**:把「并发闸」和「重试」彻底解耦。闸依然只对短探针生效,**重试对所有路径一律生效**。两条路径现在共用同一个 `retryOnTransientSpawn`,不可能再各走各的。重试预算也从 5 次(约 4.5 秒)提到 8 次(约 10.8 秒),以覆盖 npm 安装期间更长的 EBADF 窗口。

## 根因二:更新其实成功了,却被事后探针判成失败

更新流程是「探测 → 执行更新 → 再探测」。第二次探测正好落在 spawn 最不稳的窗口里,一旦它 EBADF 抛错,**整个更新就被报成失败**——哪怕 npm 已经装好了。

**修复**:**结论归更新命令自己**。事后探测只用来读取新版本号;它探不动时不再推翻已经成功的更新(安装路径同样处理)。

## 根因三:「无法检查」是误报警,不是故障

Cursor / Grok Build / Hermes Agent 没有可查询的 npm 包(`npmPackage: null`),但它们**都有自己的 `update` 命令**——即它们自管更新。界面却把这种情况和「查询失败」混在一起,统统显示成灰色的**「无法检查」**,看着像坏了。

**修复**:真正查询失败才叫「无法检查」;自管更新的显示为**「自更新」**(10 种语言均已补齐)。

## 关于「独立副本」

你本机有三份 claude:`nvm v22 → 2.1.217`(终端实际在跑)、`~/.local/bin → 2.1.218`、`nvm v24 → 2.1.207`。更新本来就会精确装到**终端在跑的那一份**的前缀下——之前它没生效,正是因为根因一、二让更新压根没成功。更新跑通后,active 那份会成为最新,这条提示自然消失。仍然多余的旧副本,提示里会给出确切路径供你手动清理(删二进制这种事不该由应用替你做)。
