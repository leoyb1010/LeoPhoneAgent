# leocodebox 1.62.0 — 「更新老是失败」的最终根因:文件描述符泄漏

1.61.0 修的两条(安装/更新没有 EBADF 重试、成功被事后探针推翻)都是真问题,但**都不是最终根因**——所以你点更新依旧无效。这一版找到了最终根因,并且是**量出来的**,不是推理出来的。

## 最终根因:会话监视器每个文件占一个 fd,fd 耗尽后 spawn 全线阵亡

在你的机器上实测(app 已运行约 3 小时):

```
进程已打开 fd ≈ 22,209   其中 22,182 个是普通文件
其中 19,021 个全部来自:~/.claude/projects/-Users-leoyuan--claude-mem-observer-sessions
该目录实际文件数:      19,021   ← 一个文件,一个 fd,完全一一对应
```

会话监视器用的是 **chokidar**,它在 macOS 上会为**每一个被监视的文件**持有一个打开的文件描述符。对照实验(同机、同 Node):

| 监视方式 | 2000 个文件 | fd 增量 |
|---|---|---|
| chokidar(旧) | 2000 | **+2000** |
| 原生 `fs.watch(recursive)` | 2000 | **+0** |

于是形成一个**随运行时长恶化的故障**:app 刚启动 fd 很少,更新能成功(1.61.0 装机后我实测 claude 2.1.217→2.1.220 就成功了);跑上几小时后 fd 被耗尽,**此后任何 `spawn` 都必然 EBADF**——`which`、`npm`、`--version` 探测,全部起不来。

这解释了为什么这个问题被修了很多次都没好:历次修复(包括 1.61.0)都把 EBADF 当成**瞬时竞态**,加重试、加串行、加退避。但这是**资源耗尽**——重试再多次也一样失败,只是把失败推迟到 54 秒之后。

## 修复
把会话监视换成**每个根目录一个原生递归 `fs.watch`**,不再逐文件持有描述符。功能不变(仍然实时感知会话新增/变更),但 fd 占用从「和会话文件数一样多」降到**常数级**。

## 验证
- 对照实验如上表(同机实测,非推断)。
- 新增回归测试:监视 500 个文件的目录,断言新增 fd < 50(逐文件监视会加 ~500)。这条测试会在任何人把逐文件监视改回来时立刻失败。
- 门禁全绿:typecheck 0、ESLint 0、client 71/71、server **337/337**、生产构建通过。

### 装机实测(1.62.0)
| 指标 | 1.61.0(跑 3 小时后) | 1.62.0(同一台机、同一个 19k 目录) |
|---|---|---|
| 进程 fd 总数 | 22,209 | **45** |
| 该 19k 目录占用的 fd | 19,021 | **0** |
| `POST /cli/opencode/update` | ✗ 54 秒后 `spawn EBADF` | ✓ **5.4 秒,1.18.4 → 1.18.5** |
| `POST /cli/gemini/update` | — | ✓ **0.51.0 → 0.52.0** |

两次更新跑完后 fd 仍为 55,不再随时间增长。

## 你需要知道的
- 那个 19,021 个文件、1.2 GB 的目录是 **claude-mem 插件**在持续写入的,而且还在增长。leocodebox 现在不会再被它拖垮,但这个目录本身是否需要清理,由你决定(不是 leocodebox 生成的,我不会替你删)。
- 装上本版后,**先退出并重开 app**,让泄漏的 fd 释放掉。
